# AGENTS.md

Инструкция для AI coding agents. Проект: инструмент совместного владения техникой под названием "Братский прокат" (MVP).  
Источник истины: `PRODUCT.md`, `ARCHITECTURE.md`, `ADR-001.md`.

## 1. Project Overview

**Назначение:** Веб-приложение для совместного владения редко используемой техникой (мотоциклы, лодки, квадроциклы) внутри закрытой группы собственников: календарь бронирований, учёт мото-часов, разделение расходов.

**Технологический стек:**
- Фронтенд: React + Vite + TypeScript
- Стилизация: Tailwind CSS + shadcn/ui (или Headless UI)
- Управление состоянием: Zustand (UI), React Query (серверные данные)
- Бэкенд: Vercel Serverless Functions (Node.js)
- База данных: Supabase Free Tier (PostgreSQL + Auth)
- Тестирование: Vitest + React Testing Library + Playwright
- Хостинг: Vercel Hobby (без привязки карты)

**Целевая аудитория:** частные лица (B2C), несколько десятков пользователей в первый год.

## 2. Architecture

**Архитектурные принципы:**
- Тонкий клиент + серверные функции + управляемая БД.
- Клиент не обращается к Supabase напрямую — все запросы идут через `/api/`.
- Бизнес-логика и валидация живут в API-функциях, не в компонентах.
- Изоляция данных между группами через RLS на уровне БД.

**Структура проекта:**
```
client/         # React + Vite приложение
api/            # Vercel Serverless Functions
supabase/       # Миграции и seed SQL
tests/          # E2E (Playwright)
```

**Правила организации модулей (client/src):**
- `features/` — доменные модули (`auth`, `groups`, `equipment`, `bookings`, `expenses`). Каждый содержит свои компоненты, Zustand-хранилища, React Query хуки, формы.
- `components/ui/` — общие бездоменные UI-компоненты (кнопка, инпут, модалка).
- `pages/` — маршруты (`/`, `/login`, `/register`, `/groups/:id`, `/bookings`).
- `stores/` — глобальные Zustand-сторы (например, `auth`).
- `hooks/` — глобальные хуки (`useAuth`, `useBookingCalendar`).
- `lib/` — клиенты Supabase, обёртка `fetch`, queryClient.
- `types/` — общие TypeScript-типы.

**Разделение ответственности:**
- Компоненты: отображение и ввод, не знают про SQL.
- Client data layer: React Query + fetch к `/api/`, Zustand для UI-состояния.
- API-функции: приём запросов, валидация (Zod), бизнес-правила, обращение к Supabase.
- Supabase: хранение, RLS-политики, аутентификация.

## 3. Coding Standards

**JavaScript/TypeScript:**
- Весь код на TypeScript. `any` допустимо только временно с комментарием `// TODO`.
- Strict mode включён в `tsconfig.json`.
- Импорты сортируются (ESLint/Prettier).

**React:**
- Функциональные компоненты + хуки. Классовые компоненты не используются.
- Props типизируются через интерфейсы или типы.
- Нет логики бизнес-правил внутри компонентов.

**Организация компонентов и хуков:**
- Общие UI-компоненты в `components/ui/`, без бизнес-логики.
- Доменные компоненты внутри `features/*/components/`.
- Хуки внутри `features/*/` или глобально в `hooks/`, если переиспользуются между фичами.

**Работа с типами:**
- Общие типы в `client/src/types/`.
- Доменные типы могут располагаться внутри соответствующей `features/*/types.ts`.
- Типы ответов API соответствуют формату `{ data: ..., error: ... }`.

**Обработка ошибок:**
- Клиент: глобальный React `ErrorBoundary`, тост-уведомления при сбоях React Query, редирект на `/login` при истечении сессии.
- API: `try/catch`, HTTP-статусы (400, 401, 403, 404, 500), JSON `{ error: "message" }`.
- Валидация входных данных в API-функциях через Zod.

## 4. State Management

**Глобальное состояние (Zustand):**
- Только UI-состояние: открытые модальные окна, выбранный слот в календаре, черновики форм.
- Сессия аутентификации дублируется в Zustand-сторе `auth` для быстрого доступа.
- Не хранить в Zustand данные, которые уже кэшируются React Query.

**Серверные данные (React Query):**
- Списки техники, броней, расходов, групп.
- Кэширование, фоновая перезагрузка, состояния `isLoading` / `isError`.

**Локальное состояние (`useState` / `useReducer`):**
- Временное состояние внутри одного компонента (фокус инпута, локальная валидация формы до отправки).

## 5. Testing

**Какие тесты писать:**
- Юнит-тесты (Vitest): утилиты, Zod-схемы, расчёт мото-часов, разделение расходов.
- Компонентные тесты (Vitest + React Testing Library): модалки, формы, календарь.
- E2E (Playwright): критичные сценарии — вход → создание группы → добавление техники → бронирование → учёт часов → история.

**Команды:**
- `npm test` — юнит-тесты и компонентные тесты.
- `npx playwright test` — E2E тесты.

**Проверки после изменений:**
- Пройти TypeScript проверку (`tsc --noEmit` или скрипт в `package.json`).
- Запустить юнит-тесты для затронутых модулей.
- Запустить E2E для критичных сценариев, если изменён пользовательский поток.

## 6. Development Workflow

**Как исследовать задачи:**
1. Прочитать `PRODUCT.md`, `ARCHITECTURE.md`, `ADR-001.md`.
2. Определить, к какой фиче (`features/*`) относится задача.
3. Проверить, есть ли существующие компоненты/хуки/сторы для переиспользования.

**Когда составлять план:**
- Перед началом любой функции, затрагивающей более одного модуля.
- Перед изменением API-контрактов или схемы БД.
- Перед добавлением новой зависимости.

**Как реализовывать функциональность:**
1. Создать/обновить SQL-миграцию в `supabase/migrations/` (если затрагивается БД).
2. Добавить или обновить API-функцию в `api/` с валидацией Zod.
3. Добавить React Query хук и/или Zustand стор в `client/src/features/*/`.
4. Добавить компоненты и страницу.
5. Написать тесты (юнит + компонент + E2E при необходимости).
6. Проверить TypeScript и запустить тесты.

**Code Review:**
- Проверять соответствие структуре `features/*`.
- Убедиться, что нет прямого доступа к Supabase из клиента.
- Убедиться, что валидация входа в API-функциях через Zod.
- Убедиться, что TypeScript проверка пройдена.
- Проверить финальный `git diff` перед коммитом.

## 7. Restrictions

**Нельзя менять без моего согласования:**
- Технологический стек (фреймворк, язык, БД, хостинг).
- Архитектурное решение «все запросы через `/api/`, нет прямого доступа клиента к Supabase».
- Выбор Zustand + React Query для управления состоянием.
- Структура каталогов верхнего уровня (`client/`, `api/`, `supabase/`).

**Нельзя добавлять без необходимости и согласования:**
- Новые npm-пакеты (за исключением dev-зависимостей, уже указанных в стек).
- Новые библиотеки управления состоянием, UI-киты, фреймворки тестирования.
- Новые паттерны или абстракции без явной выгоды.

**Требуют моего подтверждения:**
- Изменение способа аутентификации (Supabase Auth vs кастомный JWT).
- Изменение схемы БД (новые таблицы, изменение связей, удаление полей).
- Добавление уведомлений, мобильных приложений, маркетплейса, платежей (вне MVP).
- Изменение правила «один слот — одна техника».

## 8. Completion Requirements

**Что агент должен сообщать после реализации:**
- Краткое описание того, что было сделано.
- Какие файлы созданы или изменены.
- Какие проверки выполнены (TypeScript, тесты, линтер).
- Какие нерешённые проблемы или риски найдены.
- Требуется ли моё согласование на какое-либо архитектурное изменение.

**Как описывать проверки и найденные проблемы:**
- Указывать команды, которые были запущены, и их результат.
- Не утверждать, что проверка прошла, если она не была выполнена.
- Явно сообщать о нерешённых вопросах (например, аутентификация, роли внутри группы, хранение фото).

**Обязательные правила выполнения:**
- Не модифицировать не связанные с задачей файлы.
- Не вводить новые зависимости без одобрения.
- Не менять ключевые архитектурные решения без одобрения.
- Никогда не удалять существующий функционал молча.
- После изменений в TypeScript запускать TypeScript проверку.
- После реализации запускать соответствующие тесты.
- Перед финишем проверить финальный `git diff`.
