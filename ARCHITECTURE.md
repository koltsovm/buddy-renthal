# ARCHITECTURE.md

## 1. Общая архитектура
Приложение построено по схеме «тонкий клиент + серверные функции + управляемая база данных».

```
+----------------+      HTTPS/API      +---------------------+      SQL/RLS      +----------------+
|   Клиент       | <------------------> |  Serverless API     | <---------------> |  Supabase      |
| (React + Vite) |      (Vercel)        |  (Node.js, /api/)   |      (PostgreSQL) |  (БД + Auth)   |
+----------------+                      +---------------------+                   +----------------+
```

- **Клиент:** статический React-сайт, раздаётся через Vercel. Содержит лендинг, форму входа/регистрации и защищённый кабинет пользователя.
- **API-слой:** Vercel Serverless Functions. Все запросы к данным проходят через эти функции (нет прямого доступа браузера к Supabase).
- **Данные:** Supabase Free Tier — PostgreSQL с Row Level Security (RLS) и аутентификацией.

## 3. Принципы разделения ответственности

| Слой | Ответственность |
|------|-----------------|
| **Клиент (компоненты)** | Отображение данных, обработка пользовательского ввода, маршрутизация, локальное UI-состояние. Не знает про SQL. |
| **Клиент (слой данных)** | React Query для кэширования серверных данных, вызов API-функций через `fetch`, Zustand для UI-состояния. |
| **API-функции** | Получение запросов от клиента, валидация входных данных (Zod), бизнес-логика (проверка пересечения броней, расчёт часов, права доступа), обращение к Supabase. |
| **Supabase (БД)** | Хранение данных, целостность, индексы, RLS-политики, аутентификация пользователей. |

## 4. Организация компонентов
- **Атомарный подход:** общие UI-компоненты (кнопка, инпут, модальное окно) в `components/ui`.
- **Доменные компоненты:** специфичные для фичи (календарь броней, форма техники) внутри соответствующей папки `features/*/components`.
- **Страницы:** в `pages`, собирают компоненты и подключают данные через хуки.

## 5. Стратегия управления состоянием
- **Серверное состояние** (список техники, брони, расходы): **React Query** — кэширование, фоновая перезагрузка, обработка состояний загрузки/ошибки.
- **Клиентское UI-состояние** (открытые модальные окна, выбранный слот в календаре, черновик формы): **Zustand** — лёгкие сторы без бойлерплейта.
- **Сессия аутентификации:** хранится в Supabase Auth, дублируется в Zustand-сторе `auth` для быстрого доступа на клиенте.

## 6. Взаимодействие с API
- Все запросы от клиента идут на свои Serverless Functions по путям `/api/groups`, `/api/bookings` и т.д.
- Клиент не имеет прямого доступа к Supabase из браузера.
- Формат ответов: стандартизированный JSON `{ data: ..., error: ... }`.
- Валидация входных данных в функциях — библиотека `zod`.

## 7. Обработка ошибок
- **Клиент:** глобальный React `ErrorBoundary`, тост-уведомления при сбоях запросов (через React Query), редирект на `/login` при истечении сессии.
- **API:** `try/catch`, возвращение HTTP-статусов (400, 401, 403, 404, 500) и JSON с описанием ошибки.
- **Валидация:** Zod-схемы на входе в каждую функцию, защита от некорректных данных в БД.

## 8. Стратегия тестирования
| Уровень | Инструмент | Объём |
|---------|------------|-------|
| Юнит-тесты | Vitest | Утилиты, Zod-схемы, расчёт мото-часов, разделение расходов |
| Компонентные тесты | Vitest + React Testing Library | Отдельные UI-компоненты (модалки, формы, календарь) |
| E2E | Playwright | Критичные сценарии: вход → создание группы → добавление техники → бронирование → учёт часов → история |

## 9. Развёртывание
- **Фронтенд:** Vercel Hobby (статический сайт из сборки Vite).
- **Бэкенд:** Vercel Serverless Functions (папка `api/`).
- **База данных:** Supabase Free Tier.
- **CI/CD:** GitHub Actions (проверка линтера, тестов, деплой при `push` в `main`).

## 10. Допущения и открытые вопросы
- Способ аутентификации (Supabase Auth vs кастомный JWT) — требует финального решения.
- Роли внутри группы (владелец/участник с разными правами) — не детализировано в MVP.
- Хранение фото техники — Supabase Storage или внешний S3-совместимый сервис — открыто.
